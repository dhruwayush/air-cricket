# Air Cricket

A 3D cricket batting game in one HTML page, played in the browser (GitHub Pages) and as an Android app (Capacitor). The README describes the gameplay; this file covers what you need to change it safely.

## Files

| Path | Edit it? |
| --- | --- |
| `src/game.html` | **Yes, this is the game source.** All HTML, CSS and JS in one file. |
| `index.html` | **No, it's generated** by `python3 tools/build_page.py`. It's committed because GitHub Pages serves it, so rebuild and commit it with every change to `src/game.html`. |
| `tools/players.py` | Blender script that builds, rigs and animates the players and exports `tools/build/*.glb`. |
| `tools/build/*.glb` | Generated by `players.py`, committed. `build_page.py` embeds them as base64. |
| `tools/voice_lines.py` | Every commentary line (English and Hindi), plus the edge-tts recording script. |
| `sounds/voice/<group>/<id>.mp3` | Recorded commentary clips, embedded by `build_page.py`. |
| `tools/prepare-www.mjs` | Builds `www/` for Android: swaps the CDN scripts and Google Fonts for copies from `node_modules`. |
| `www/`, `android/app/build/` | Build output, not tracked. |

## Commands

```sh
python3 tools/build_page.py        # src/game.html (+ models, voice clips) -> index.html
python3 tools/players.py           # rebuild the players (needs: pip install bpy==4.2.0, Python 3.11)
npm install && npm run apk         # Android debug APK (Node 22, JDK 21, Android SDK)
python3 -m http.server 8000        # then open http://localhost:8000/ (the camera modes need https or localhost)
```

There are no unit tests. Check changes by rebuilding `index.html` and loading it in a browser: headless Chromium via Playwright works (`/opt/pw-browsers`, launch with `--use-angle=swiftshader --enable-unsafe-swiftshader` for WebGL). Look for console errors and play a few balls.

## three.js is r128: use the r128 API

The game is pinned to **three.js r128** (`package.json`, the CDN `<script>` tags in `src/game.html` and the swap table in `tools/prepare-www.mjs` must all agree). Most three.js docs and examples online, and the three.js skill, describe newer releases. In r128:

- three.js is the global `THREE` from `<script>` tags, not ES modules. Loaders and utils come from `examples/js/` (`THREE.GLTFLoader`, `THREE.SkeletonUtils`). Newer releases removed `examples/js/` completely.
- Colour: `renderer.outputEncoding = THREE.sRGBEncoding` and `texture.encoding = THREE.sRGBEncoding`, not `outputColorSpace` / `colorSpace`. Colours are written in sRGB and converted with `lin(hex)` (`convertSRGBToLinear`) before lighting.
- Lights use the old (non-physical) intensity units; the floodlight values are tuned for that.
- `BufferGeometryUtils` isn't loaded. Load it from the same `three@0.128.0/examples/js/` path if you need it, and add it to `prepare-www.mjs` as well.

To add a three.js script, add the CDN `<script>` tag (pinned to 0.128.0) **and** its entry in the `scripts` table in `tools/prepare-www.mjs`, or the Android build fails ("index.html no longer contains").

## Conventions in `src/game.html`

- Everything runs inside one closure `(() => { ... })()`, so nothing is global. Debug from outside by hooking `THREE` (see `.claude/skills/mobile-performance/measure.mjs`).
- Materials: use the `std(colour, rough, metal, extra)` helper (MeshStandardMaterial) for lit surfaces and `basic({...})` for unlit ones (lines, signs, glows). Textures are drawn on canvases with `canvasTex(...)`. No image files.
- Input goes through `requestShot(direction)` and `setGuard(position)`. New controllers call those and never touch game logic.
- **Randomness:** gameplay that the daily challenge or a replay code depends on (deliveries, bowlers, fields) must use the seeded `rng(seed)` generator, never `Math.random()`. Otherwise players with the same seed get different balls. `Math.random()` is fine for visuals only (crowd, flags, idle animation offsets).
- Graphics levels: `applyGfx()` switches High/Fast (pixel ratio, shadows); Auto drops to Fast if the median frame takes longer than 1/40 s. Keep new effects cheap on Fast.
- Comments explain the *why* in plain words, matching the README's tone. Keep code dense and match the style around it.
